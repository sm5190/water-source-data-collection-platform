# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Evidence-grounded, human-reviewed research workflow that collects a standardized 32-field water-source dataset per city. Core principle: **the AI is not the source** — every accepted value must trace back to evidence (utility, government, technical, regulatory, academic, or other approved source).

This is an early scaffold. Apart from `extract`, graph nodes in `agents/nodes.py` are pass-through stubs (discover/acquire produce no evidence yet), no real `LLMGateway` implementation exists, Apify and Computer Use acquirers raise `NotImplementedError`, the VT LLM request/response schema is a placeholder (see TODO in `llm/vt_client.py`), and the Docling adapter and most SQLAlchemy/pgvector models described in `docs/ER_MODEL.md` do not exist in code yet.

## Commands

Uses `uv`, Python >=3.12. Package lives in `src/water_source_research` and is installed into `.venv` in editable mode by `uv sync` (hatchling build backend), so `uv run …` works from any shell without `PYTHONPATH`.

```bash
cp .env.example .env
docker compose up -d postgres minio            # pgvector Postgres 16 + MinIO
docker compose --profile discovery up -d searxng  # optional, SearXNG on :8080
uv sync --all-extras                           # dev (pytest/ruff), docs (docling), ui (streamlit)
uv run pytest                                  # all tests
uv run pytest tests/test_rules_engine.py::test_percentage   # single test
uv run ruff check .                            # line-length 100, target py312
uv run uvicorn water_source_research.api.main:app --reload  # API (enqueues runs; needs migrated DB)
uv run python scripts/run_research_worker.py [--once] [--concurrency N]  # executes queued runs
uv run python scripts/run_city.py Toronto      # dev: run the graph inline for one city, no queue
uv run streamlit run src/water_source_research/ui/app.py   # dashboard on :8501 (needs API + worker; RESEARCH_API_URL)
uv run python scripts/build_city_catalog.py "<path>/Sarina Water Source.xlsx"  # regenerate config/cities.yaml
uv run alembic upgrade head                    # apply migrations (uses DATABASE_URL)
uv run alembic revision --autogenerate -m "…"  # review it; run `alembic check` against BOTH SQLite and Postgres
uv run python scripts/run_procedure_worker.py --once   # distillation jobs, pending embeddings, lifecycle sweep
docker compose exec postgres psql -U water -d water_source -c "CREATE DATABASE water_source_test"  # once
TEST_DATABASE_URL=postgresql+psycopg://water:water@localhost:5432/water_source_test uv run pytest tests/integration
# ^ Postgres/pgvector tests (skipped without the env var); they migrate up and back down to empty
```

Run everything from the repo root: `services/field_state.py` loads `config/field_definitions.yaml` via a relative path. Config files are resolved from the repo root (`core/paths.py`), so commands work from any directory. Alembic's `prepend_sys_path` needs `path_separator = os` because the repo path contains spaces.

## Architecture

**City runs are asynchronous (`research_queue/`)**: `POST /research/city` enqueues and returns 202 + `run_id` (200 with the existing run if that city — normalized city|country — is already QUEUED/RUNNING; enforced by a partial unique index). Clients poll `GET /research/runs/{run_id}` and fetch `/result`; `POST …/cancel`; `GET /research/queue/stats`. Workers (`ResearchWorker`, any number of processes/hosts) claim jobs from the `research_jobs` table with `SELECT … FOR UPDATE SKIP LOCKED` + a time-limited lease, run at most `worker_concurrency` graphs each (optional `max_running_global` cap via Postgres advisory lock), heartbeat to extend the lease, and retry failures with exponential backoff up to `max_attempts`. All state changes after claim are fenced by `lease_owner`, so a stalled worker that lost its lease can't overwrite anything. The graph is compiled with a checkpointer (`research_queue/checkpointing.py`: `AsyncPostgresSaver` on Postgres, tables created by its own `setup()`, not Alembic; `InMemorySaver` otherwise) using thread_id = run_id: a retried run resumes from the last completed step, and a run that finished but wasn't recorded is just recorded. Checkpoints are deleted after success unless `keep_checkpoints`. On shutdown, in-flight runs get `shutdown_grace_seconds` and are then released without consuming an attempt. Lease times use the app clock (keep hosts NTP-synced). On Windows, psycopg async needs a selector loop — use `checkpointing.run_async`. Settings: `research_queue/config.py` (`RESEARCH_QUEUE__*`). Tests: `tests/queue_helpers.py` (`Clock`, `Probe` node instrumentation, `Crash` for simulated process death).

**Dashboard (`ui/`, Streamlit)**: talks only to the API via `ui/client.py::ResearchApiClient` (inject a fake via `st.session_state["client"]`; tests use `streamlit.testing.v1.AppTest`). City dropdown = `config/cities.yaml` (generated from the project workbook; `services/city_catalog.py`, `GET /research/cities`). Progress = `research_run_steps`: the worker streams the graph (`astream(stream_mode="updates")`) and records each completed node with a compact summary from `research_queue/steps.py::summarize_step` (`GET /research/runs/{id}/steps`). Human review log and field-aware provenance are derived from the stored run result + trusted events in `reporting/run_views.py` (`GET …/review`, `GET …/fields`); citations come only from claim `EvidenceRef`s. The dashboard polls with `st.fragment(run_every=…)` only while a run is QUEUED/RUNNING.

**Workflow (LangGraph, `agents/`)**: `plan → discover → acquire → extract`, then extract routes back to `discover` while `fields_needing_evidence` is non-empty and `discovery_rounds < MAX_DISCOVERY_ROUNDS_PER_CITY`, else `validate` (which flags still-missing fields for `human_review`) → `finalize`. State is the `GraphState` TypedDict (`agents/state.py`) and carries the run: `run_id`, serialized `research_state` (CityResearchState), `evidence_chunks`, `seen_evidence`; LangGraph drops keys not declared there. Nodes return `{**state, ...}`; `plan` fills in `run_id`/`research_state` if the caller didn't. `build_graph(gateway=, context_service=, max_discovery_rounds=, procedure_memory=, usage_tracker=, run_recorder=, capability_availability=)` injects dependencies; the default `UnconfiguredGateway` raises once a READY bundle reaches it. Nodes append **trusted workflow events** to `state["events"]` via `schemas/events.py::append_event` (allow-listed attrs, URLs stripped to scheme/host/path, secrets redacted); these are the only input to procedure distillation, so new nodes that call tools must emit `TOOL_CALL` events with a `Capability`. `human_review` applies `review_decisions` (APPROVED/CORRECTED/REJECTED) — the only current path to RESOLVED.

**Extraction path**: `extract` (built by `make_extract_node`) calls `ContextService.get_context(run_id=, field_key=, operation=EXTRACT, graph_state=)` per field concurrently. Bundle status: `NOT_NEEDED` → skip; `NO_SUFFICIENT_EVIDENCE` → field goes to `fields_needing_evidence`; `READY` → `LLMGateway.extract(bundle, run_id=, field_key=)` (Protocol in `llm/gateway.py`), claims become candidates and `bundle.consumed` is added to `seen_evidence`. A READY bundle that yields no claims is also sent back to discovery (its chunks are now seen, so they aren't re-sent). Re-entry only retries `fields_needing_evidence`. OTel spans: `graph.extract` → `context.get_context` → `context.load_state`, `context.bundle_create` → (on cache miss) `context_manager.build` → `context.retrieval`/`ranking`/`dedupe`/`budgeting`. Tests capture spans with the `spans` fixture in `tests/conftest.py`.

**Field model — keep three places in sync**: the 32 fields are defined in `config/field_definitions.yaml` (key, `field_type` grouping used by procedural memory, subject `city`/`supply_record`, type, enum `allowed` values, `derived` flag, `depends_on`, and `keywords` used for evidence ranking; loaded as `FieldDefinition`s by `load_field_definitions`), mirrored by `schemas/standardized.py::StandardizedWaterSourceRow` (export row), and `tests/test_field_state.py` asserts the count is exactly 32. Derived fields (`percentage_total_population`, `source_withdrawal_percentage`) are computed by `services/rules_engine.py`, not extracted.

**Per-field resolution state (`schemas/`)**: each field has a `FieldState` with a `FieldResolutionStatus` (UNRESOLVED → CANDIDATE / CONFLICT / HITL_REQUIRED → RESOLVED / NOT_APPLICABLE). Candidates are `FieldClaim`s carrying `ValueStatus` (KNOWN/UNKNOWN/NOT_APPLICABLE), `ValueOrigin` (REPORTED/CALCULATED/ESTIMATED/ALLOCATED), confidence, and `EvidenceRef`s. A field counts as unresolved while UNRESOLVED, CONFLICT, or HITL_REQUIRED. On export, UNKNOWN → `"Unknown"` and NOT_APPLICABLE → `"N/A"` (`rules_engine.export_missing`).

**Domain model (`docs/ER_MODEL.md`)**: the central entity is `SupplyRecord` = one city receives water from one hydrologic source through one utility. Provenance chain: SourceDocument → artifact → EvidenceSpan → FieldClaim → FieldResolution → accepted data.

**Provider tiers** — adapters are small classes with a common async method:
- Discovery (`discovery/`, `async search(query, limit) -> list[SearchResult]`): SearXNG, OpenAlex, Crossref, Semantic Scholar by default; Firecrawl/Apify optional.
- Acquisition (`acquisition/`, `async acquire(url) -> AcquiredDocument`), in escalation order: direct HTTP (trafilatura, BeautifulSoup fallback; HTML only) → Docling for PDFs → Firecrawl → Apify actor → Computer Use for interactive portals. Each sets `acquisition_method` (e.g. `DIRECT_HTTP`, `FIRECRAWL`).
- LLM routing (`llm/`): `OpenAIReasoner.structured()` (Responses API `parse` into a Pydantic schema) for planning, extraction, conflict resolution, validation; `VTLLMClient` (cheap, OpenAI-chat-shaped) for relevance filtering, classification, query generation, metadata cleanup.

**Cross-cutting**: settings come from `core/config.py::get_settings()` (pydantic-settings, `.env`, cached), including per-city budgets (`MAX_OPENAI_*_TOKENS_PER_CITY`, `MAX_FIRECRAWL_CREDITS_PER_CITY`). `services/evidence.py::chunk_document` turns an `AcquiredDocument` into `EvidenceChunk`s.

**Context manager (`context_manager/` package: `manager.py` builds bundles, `store.py` persists them, `service.py` is the graph entry point; import from `water_source_research.context_manager`)**: every LLM call should get its prompt context from `ContextManager().build(ContextTask(purpose, target_fields), city_state, chunks, seen)` (the graph goes through `ContextService`). It is pure/in-memory. Per `ContextPurpose` it prunes targets (already-resolved, derived, nothing-to-resolve → `bundle.skipped_fields`; `bundle.is_empty` means skip the LLM call), adds resolved anchor/`depends_on` values as one-line facts, and then either ranks chunks (EXTRACT: keyword BM25 × source-type prior × city/digit heuristics, per-target seed pass, dedupe, per-source cap, sentence excerpting, token budget) or lists candidate/selected claims (RESOLVE_CONFLICT / VALIDATE: all claims kept, passages shrunk). Sources get `S#` ids; `bundle.evidence_ref("S1")` maps an LLM citation back to an `EvidenceRef`. Callers persist `bundle.consumed` into `seen` so the same (chunk, field) isn't re-sent. The manager never calls a model; LLM response caching belongs in the LLM layer, keyed by `bundle.fingerprint`/`bundle_id`.

**Bundle persistence (`context_manager/store.py`, `db/`)**: `ContextBundleStore(engine).get_or_build(manager, task, state, chunks, seen)` (or `aget_or_build` from async nodes) reuses a stored bundle from the `context_bundles` table when `ContextManager.cache_key(...)` matches. The key covers the policy signature (`RETRIEVAL_POLICY_VERSION`, manager config, token estimator, field definitions) plus only the inputs the build reads: target/anchor/`depends_on` field states, and for EXTRACT the chunk contents and `seen` pairs for the targets. **Bump `RETRIEVAL_POLICY_VERSION` when changing scoring/excerpting/rendering logic** so old bundles aren't reused. Concurrency: a per-key in-process lock builds each bundle once, and the unique `cache_key` constraint settles races across processes (the loser returns the winner's row). `db/` is the repo's first DB code: `db/models.py` (SQLAlchemy 2.x declarative, JSON→JSONB on Postgres) and `db/session.py` (`get_engine()` from `DATABASE_URL`, `init_db()` = `create_all`, schema changes go through Alembic in `migrations/`; `init_db()` = `create_all` for tests/dev). Dialect-specific DDL (the pgvector HNSW index) is declared on the model with `.ddl_if(dialect="postgresql")`, and `db/models.py::include_object_for` keeps Alembic from reporting it as drift on other backends — SQLite-only checks can't catch Postgres drift, so `tests/integration` includes a Postgres drift test). Store tests run on a file-backed SQLite in `tmp_path`. OpenTelemetry (`observability/otel.py`) is intended as the canonical audit layer (run/city/field IDs, provider/model, tokens, latency, cost, confidence, HITL events).

**Procedural memory (`procedures/`)**: reusable *research strategies* learned from validated runs — advisory planning guidance only, never evidence, field state, or an LLM cache. Keep those boundaries: procedure text must never get an `S#` id or satisfy an evidence requirement (`ContextTask.procedure_hints` render only for PLAN/QUERY_GENERATION, in their own section).
- Read path: `graph.plan` → `ProcedureMemory.retrieve(RetrievalRequest)` once per field type with unaccepted fields → SQL metadata filter (ACTIVE, task/field type, water type, `min_workflow_version`, required capabilities) → cosine over survivors only (pgvector `<=>` on Postgres, Python on SQLite) → `RankingPolicy` (Wilson lower bound, EWMA recent success, recency, correction penalty) → ≤`max_results`. `retrieve` never raises (degraded → default strategy). `choose_strategy` drops capabilities not in `available_capabilities()`; `discover` renders query templates into `planned_queries`.
- Write path (async, soft): `finalize` → `RunRecorder` persists `research_runs`/`run_events` and enqueues `distillation_jobs` (key = hash(trajectory_id, `DISTILLER_VERSION`)) → `DistillationWorker`: build trajectory from events → `EligibilityPolicy` → `DeterministicDistiller` → schema + `check_grounding` + `check_safety` (no URLs/domains/secrets; queries must template to observed, generic-vocabulary searches) → `MergeEvaluator` (same `procedure_key` = metadata + capability plan; structural Jaccard required, embedding cosine only as an extra guard) → CANDIDATE → `LifecyclePolicy` (support runs/cities, correction rate; `require_human_approval` → AWAITING_APPROVAL, approve via `POST /procedures/versions/{id}/approve`).
- Concurrency/idempotency live in the DB: unique `procedure_key`, `(procedure_id, version)`, origin `distillation_key`, usage `(version, run, field)`; partial unique index = one ACTIVE version per procedure; conditional UPDATEs for job claims/transitions; SQL increments for stats. Recipes are immutable; versions change only status/stats/embedding.
- Usage: retrieved → selected → applied → outcome (once) in `procedure_usages`; only applied usages move success/failure stats.
- All thresholds are in `procedures/config.py::ProcedureMemorySettings` (`PROCEDURE_MEMORY__*` env, validated at startup; disabled by default). Version constants are in `core/versions.py`; capabilities (vendor-independent) in `core/capabilities.py`.
- Tests: `tests/procedure_helpers.py` (FakeEmbedder, `seed_version`, `run_state` event builders); metrics via the `metric_points` fixture.
